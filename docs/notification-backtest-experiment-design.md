## 1. 対象期間（2案を両方採用）

### Period B（梅雨期間）

```
2026-06-04（近畿地方 梅雨入り） 〜 2026-07-08（近畿地方 梅雨明け）
= 35日間
```

気象庁発表として複数の報道で確認済み（2026年は平年より梅雨入り2日早く、梅雨明け11日早い）。

出典:
- [お天気.com「【2026年(令和8年)】近畿(大阪)梅雨入り・梅雨明け」](https://hp.otenki.com/8307/)
- [tenki.jp「近畿地方で梅雨明け」(2026-07-08)](https://tenki.jp/forecaster/m_shimofuku/2026/07/08/39642.html)

### Period C（Single Runs API提供開始直後・固定長1ヶ月）

```
2026-04-02（Single Runs APIアーカイブ提供開始日、動かせない基準点） 〜 2026-05-02
= 30日間
```

開始日はSingle Runs APIの技術的な提供制約そのものであり、人間・AIどちらの裁量も
介在しない固定点である。長さ（30日）は「1ヶ月」という単純な規則で、結果を見ずに
決定した。

### 2期間を採用する理由

Period Bは実際の梅雨（降雨量が多い時期）、Period Cは梅雨入り前（相対的に降雨が
少ない時期）にあたる。両方を評価することで、「降雨の多寡が異なる時期で、
staticFloodHazardによる通知抑制効果がどう変わるか」という比較軸を持てる
（単に2つの期間を試すこと自体が目的ではなく、この対比に研究上の意味がある）。

## 2. 雨量閾値（Set C: 激しい雨基準）

| 項目 | 値 | 根拠 |
|---|---|---|
| hourlyRainfallThresholdMm (1h) | **30mm** | 気象庁「雨の強さと降り方」表の「激しい雨」区分下限（`data/README.md`に出典記載済み: https://www.jma.go.jp/jma/kishou/know/yougo_hp/amehyo.html ） |
| accumulated3hThresholdMm (3h) | **60mm** | 1hの3倍。**一次資料による独立の裏付けなし**（技術確認用の暫定設定(10/20/30mm)と同じ比率をそのまま踏襲した経験則） |
| accumulated6hThresholdMm (6h) | **90mm** | 1hの6倍。同上、独立の裏付けなし |

**重要な限界（卒論に明記すること）**: 3h・6hの値は大阪市固有の公式警報基準等の
一次資料から個別に確認したものではなく、1h値からの比例計算にすぎない。この点は
研究の限界として正直に記載する。

## 5. experimentConfigの総数

```
IETD(2) × persistence(9) = 18通りのexperimentConfig
```

各experimentConfigを、Period B・Period Cそれぞれ、24地点・4方式(Method1〜4)に
適用する。

**重要（API負荷に関する発見）**: Single Runs APIから取得した予報データ
（ForecastRunSnapshot）は、閾値・IETD・継続性条件を変えて何度でも再利用できる
（`evaluateMethod()`は純粋関数であり、追加の通信を発生させない）。したがって、
experimentConfigの組み合わせを何通り評価しても、**追加のAPI呼び出しは発生しない**。
API呼び出し回数は「期間 × 地点数 × run取得頻度」だけで決まる。

## 6. API呼び出し量とレート制限

| 期間 | 日数 | 地点数 | run/日 | 呼び出し回数 |
|---|---|---|---|---|
| Period C | 30日 | 24 | 8(3時間おき) | 5,760 |
| Period B | 35日 | 24 | 8(3時間おき) | 6,720 |
| **合計** | | | | **12,480** |

Open-Meteoの無料枠（[公式Pricing](https://open-meteo.com/en/pricing)）:

```
10,000回/日、5,000回/時間、600回/分（非商用・研究利用）
```

**12,480回は1日の上限(10,000)を超えるため、2回に分けて取得する。**

- 1回目: Period C（5,760回） — 単体で1日の上限内
- 2回目: Period B（6,720回） — 単体で1日の上限内
- 2回の実行は、Open-Meteo側の日次カウンタをまたぐよう、実施日を分ける（当日中に連続実行しない）

各回とも、逐次(1件ずつ順番に)実行することで、ネットワーク遅延により自然に
1分600回・1時間5,000回の上限内に収まる見込み（人為的なスロットリング制御を
追加で実装する必要は、現時点ではないと想定している。実行時に速度超過が
確認された場合は待機処理を追加する）。
